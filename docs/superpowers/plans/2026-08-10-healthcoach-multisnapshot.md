# Отчёт по нескольким срезам — план реализации

> **Для агентов:** ОБЯЗАТЕЛЬНЫЙ СУБ-НАВЫК: superpowers:subagent-driven-development. Шаги помечены `- [ ]`.

**Цель:** коуч запускает сборку отчёта с карточки клиента, отметив галочками, какие срезы взять в работу; интерпретация видит показатели всех выбранных срезов, а не одного.

**Подход:** отчёт по-прежнему принадлежит одному срезу — самому свежему из выбранных («первичному»). Он даёт дату отчёта, верхнюю границу графиков динамики и ключ, по которому уже живут запрос, разделы черновика, отметка утверждения и заморозка. Новая таблица хранит только *набор* срезов. Меняется единственное: что попадает на вход интерпретации.

**Стек:** Python 3.12, FastAPI, Jinja2, SQLite, uv, pytest.

## Общие ограничения

- Каждое обращение к базе — внутри `with context.session() as repo:`.
- Числовую основу считает код, модель её только трактует.
- Ничего не уходит клиенту без утверждения коуча; после утверждения отчёт заморожен целиком.
- Инструмент не угадывает: если посчитать честно нельзя — говорит об этом, а не подставляет правдоподобное.
- Данные клиентов не попадают в репозиторий никогда; тестовые ФИО — выдуманные.
- Полный набор тестов зелёный на каждом коммите. База: **598 passed, 1 deselected**.
- Схема обновляется одной транзакцией; текущая версия 5 → станет 6.

## Правила свода (решения, принятые до начала)

1. **Свёртка по показателю.** Среди выбранных срезов по каждому показателю берётся самое свежее сверенное значение — ключ сравнения `(taken_on среза, id среза, taken_on измерения, id измерения)`: сначала самый свежий *срез*, и только внутри него — самый поздний забор. Дата забора вносится с бланка и с датой среза совпадать не обязана, поэтому сравнение по одной лишь дате измерения отдавало бы победу старому срезу с поздним бланком. Более ранние значения того же показателя в находки не идут: они уже видны в динамике.
2. **Показатели без распознанного идентификатора** (`analyte_id is None`) свёртке не подлежат — проходят по одному на строку, как сегодня.
3. **Анкета не объединяется.** Берётся анкета самого свежего выбранного среза, где она заполнена. Суммы по шкалам от смешанных ответов были бы выдуманными.
4. **Возраст — по дате измерения.** Целевой коридор подбирается по возрасту клиента на дату самого измерения, а не на дату отчёта. Подшкалы опросника — по дате того среза, чья анкета взята.
5. **Производные индексы — только внутри одного среза.** Индекс считается, лишь когда все его операнды пришли из одного среза; иначе он «не посчитан» с причиной. Индекс из мартовского и августовского значений не означает того, что должен означать.
6. **Набор замерзает вместе с черновиком.** После утверждения набор срезов не меняется — иначе утверждённый отчёт менялся бы задним числом.
7. **Отсутствие записей = сегодняшнее поведение.** Срез без сохранённого набора трактуется как набор из себя одного. Все существующие срезы продолжают работать без миграции данных.

**Интерфейс** (`ReportScopeRepository`, стиль соседних репозиториев):
- `set_members(self, snapshot_id: int, member_ids: Iterable[int]) -> None` — заменяет набор целиком, одной транзакцией: `DELETE` + `INSERT`. Пустой набор запрещён (`ValueError`).

Проверку «черновик утверждён» репозиторий не делает: она живёт в маршруте, как `_refuse_if_draft_is_frozen`.

**Миграция:** `MIGRATIONS[5]` создаёт таблицу, данные не трогает. Взять за образец `MIGRATIONS[4]`; проверить, что откат прерванной миграции работает (тест в `test_migration.py` на это уже есть — повторить его для версии 6).

**Тесты:** набор сохраняется и читается; повторный `set_members` заменяет, а не добавляет; пустой набор — `ValueError`; срез без записей отдаёт `[snapshot_id]`; удаление среза уносит его строки (обе стороны каскада); наборы разных срезов не пересекаются.

**Файлы:**

```python
@dataclass(frozen=True)
class ScopedInputs:
    measurements: tuple[StoredMeasurement, ...]  # свёрнутые, по одному на показатель
    answers: Answers
```

## Решения, принятые по ходу

**Возраст применяется везде.** Правило 4 распространяется и на срезы без набора: старое поведение (коридор по дате среза для анализа, сданного месяцами раньше) было просто неверным. Отчёт по одному срезу может из-за этого измениться по сравнению с прежней версией инструмента — это осознанная плата за правильный расчёт.

**Охват дат считается по датам забора, а не по размеру набора.** `covers_several_dates` включается, когда различных дат измерения больше одной, — независимо от того, сколько срезов в наборе. Значит и одиночный срез, где лежат два бланка разных дат, теперь печатает «Анализы сданы с … по …» и колонку даты там, где раньше стояло «Срез от …». Это честная подпись: отчёт, значения которого сданы в два разных дня, обязан это сказать. Плата известна: PDF пересобирается при каждой печати, поэтому у уже утверждённых отчётов такого рода титульная страница при повторной выдаче будет отличаться от той, что клиент получил в первый раз. Заморозка чисел при утверждении (следующий пункт) снимет и это.

**Числовая основа замерзает при утверждении** — отдельной задачей после этой ветки. Сегодня `report.pdf` пересобирает отчёт из живых данных при каждой печати, поэтому любое изменение базы знаний или расчёта переписывает уже выданный клиенту документ. Заморозка снимает и отложенную дыру: правка старого среза, входящего в набор, сейчас меняет утверждённый отчёт.

## Что дальше (за рамками плана)

- Набор срезов нельзя изменить с экрана черновика — только пересобрать с карточки. Если коуч будет часто менять состав, стоит перенести выбор на экран черновика.
- Подшкалы опросника берутся из одной анкеты; сравнение анкет между срезами (стало лучше/хуже) — отдельная задача.
- Порог давности не задан: коуч сам решает, брать ли полугодовалый анализ. Если окажется, что берут по невнимательности, — предупреждать при выборе срезов старше N месяцев.
