# Health Coaching MVP — дизайн

Дата: 2026-08-08
Статус: утверждён заказчиком, готов к планированию реализации

## 1. Цель

Локальный инструмент для health coaching специалиста, который собирает данные клиента
(запрос, анкета, медицинские исследования и анализы), интерпретирует показатели по
собственным превентивным интегративным референсам коуча, формирует гипотезы и
направления к профильным специалистам, и на выходе даёт PDF-отчёт клиенту с
рекомендациями по работе с врачами, коррекции образа жизни и вспомогательным практикам.

Специалист остаётся в контуре принятия решений: система готовит черновик, коуч его
правит и утверждает.

## 2. Границы MVP

### Входит

- Генератор персонального опросника в виде автономного HTML-файла
- Импорт ответов клиента
- Приём анализов в PDF (основной путь) и фото/сканах (запасной)
- Извлечение показателей с обязательным экраном сверки цифр коучем
- Детерминированный скоринг опросника по ключу
- Детерминированная сверка показателей с кастомными референсами коуча
- Интерпретация находок языковой моделью с обезличиванием данных
- Экран правки и утверждения черновика
- Сборка клиентского PDF на 5–10 страниц
- Портфолио клиента: история срезов, динамика показателей
- Справочник специальностей и доверенных врачей (виден только коучу)

### Не входит (бэклог, см. раздел 15)

- Клиентский личный кабинет и геймификация
- Рекомендации БАДов со ссылками на магазины и ценами
- Автоматическая маршрутизация блоков опросника по ответам
- Внешние ссылки на научные публикации

## 3. Пользователь и сценарии

Единственный пользователь MVP — коуч. Клиент взаимодействует с системой только двумя
способами: заполняет присланный HTML-опросник и получает итоговый PDF.

Два формата работы:

- **Разовая консультация** — верх воронки, большинство клиентов. Один срез.
- **Сопровождение от месяца до года и более** — несколько срезов, отслеживание динамики
  показателей и прогресса по запросу клиента.

Модель данных с самого начала рассчитана на второй сценарий; разовая консультация —
его частный случай с одним срезом.

## 4. Архитектура

### Форма поставки

Локальное приложение. Бэкенд на Python (FastAPI), данные в файле SQLite, интерфейс —
серверные HTML-страницы, открываемые в браузере на `localhost`. Запуск одной командой
в терминале. Ни сервера, ни регистрации, ни хранения медицинских данных у третьих лиц.

### Конвейер с двумя воротами

```
[1] Клиент                [2] Приём               [3] СВЕРКА ЦИФР — коуч
    HTML-опросник   →      файлы анализов    →     таблица показателей
    → answers.json         извлечение текста        правка ошибок чтения
                                                            ↓
[6] PDF клиенту    ←  [5] ЧЕРНОВИК — коуч  ←    [4] Детерминированный
    врачи — отдельно      правка и утверждение     движок → находки
                                                   (скоринг + референсы)
```

**Ворота 1 — сверка цифр.** Ни одно извлечённое значение не идёт в интерпретацию без
подтверждения коучем. Рядом с каждым значением показывается фрагмент исходного документа,
из которого оно взято. Значения с низкой уверенностью распознавания помечаются.

**Ворота 2 — черновик.** Клиенту уходит только утверждённый коучем текст.

### Модули

| Модуль | Ответственность |
|---|---|
| `intake` | Сборка HTML-опросника под клиента, разбор присланных ответов |
| `documents` | Приём файлов, извлечение текста, нормализация названий показателей и единиц |
| `knowledge` | Загрузка и валидация базы знаний: референсы, контекст, опросник, специалисты |
| `scoring` | Детерминированный движок: скоринг опросника, сверка с референсами → находки |
| `interpretation` | Обезличивание, вызов модели, сборка черновика |
| `report` | Сборка клиентского PDF из утверждённого текста |
| `portfolio` | Карточка клиента, история срезов, динамика |
| `storage` | SQLite и файловое хранилище документов |

### Границы ответственности

`scoring` не имеет доступа к языковой модели вообще. Числовые выводы и степени отклонений
считаются кодом и полностью воспроизводимы. `interpretation` не считает — он получает
готовые находки и превращает их в связный текст.

Каждый прогон интерпретации пишется в журнал: версия базы знаний, набор находок, промпт,
ответ модели, временна́я метка.

## 5. Модель данных

### Сущности

- **Клиент** — код вида `CL-0417`, ФИО и контакты в отдельном локальном реестре
- **Срез** — один заход клиента: анкета, документы, находки, черновик, отправленный отчёт,
  заметки коуча. Разовая консультация = один срез; сопровождение = несколько
- **Документ** — исходный файл (PDF, фото), привязан к срезу
- **Измерение** — показатель, значение, единицы, дата забора, документ-источник,
  флаг подтверждения коучем
- **Ответы опросника** — привязаны к срезу
- **Находка** — результат работы `scoring`: отклонение показателя от целевого коридора,
  степень по блоку опросника, или сработавшее производное соотношение
- **Черновик** — текст по разделам, каждый раздел помечен находками, на которых он стоит
- **Отчёт** — утверждённая версия и собранный PDF

### Динамика

Динамика получается выборкой всех измерений клиента по конкретному показателю,
отсортированных по **дате забора** (не по дате загрузки — клиент может принести анализы
полугодовой давности, и на графике они должны встать на своё место). На график
накладывается целевой коридор из референсов.

### Хранение

Один файл SQLite и папка с исходными документами рядом. Копируется и переносится целиком.
Реестр соответствий `код клиента ↔ ФИО` хранится локально и никогда не покидает машину.

## 6. База знаний

База знаний — четыре файла с разным назначением и форматом. Ключевое разделение проходит
между слоями 1 и 2: **числа проверяются кодом и воспроизводимы, смысл даёт модель.**

### Слой 1 — референсы (машиночитаемые, YAML)

Читаются модулем `scoring`, сверяются кодом, без участия модели.

```yaml
- показатель: ферритин
  синонимы: [Ферритин, Ferritin, S-Ferritin]
  единицы: нг/мл
  лабораторный_интервал: [10, 120]
  целевые:
    - условие: {пол: ж, возраст: [18, 50]}
      оптимум: [60, 90]
      дефицит: [null, 30]
    - условие: {пол: м}
      оптимум: [80, 150]
  трактовать_с: [срб]
  заметка: Растёт при воспалении — смотреть вместе с СРБ
```

Условия покрывают пол, возраст и фазу цикла. Производные показатели задаются формулой:

```yaml
- производный: кальций_калий
  формула: кальций / калий
  оптимум: [2.0, 4.0]
```

Лабораторный интервал хранится для контраста: в отчёте клиент видит рядом лабораторную
норму и целевой коридор коуча, и расхождение объясняет ценность превентивного подхода
нагляднее любого текста.

### Слой 2 — контекст (проза, Markdown)

Интегративный подход коуча: как читать паттерны, что с чем связано, почему интервалы
сужены. Не парсится — подаётся модели как контекст на шаге интерпретации.

### Слой 3 — спецификация опросника (YAML)

Блоки, вопросы, шкалы и пороги степеней отклонения. Собирается автоматически из
`Большой_интегральный_опросник.xlsx` (лист `ОПРОСНИК` и скрытые листы
`РЕЗУЛЬТАТ КЛЮЧ` и `DASS (показатели)`), дальше ведётся отдельно.

Состав опросника: около 565 вопросов в 20 блоках — организационная часть (питание,
вредные субстанции, образ жизни, препараты), 15 клинических систем (ЖКТ по отделам,
эссенциальные нутриенты, углеводный обмен, надпочечники, щитовидная железа,
сердечно-сосудистая система, почки и мочевой пузырь, иммунная система, мужское и
женское здоровье, нарушение сна) и 5 дополнительных опросников (системное воспаление,
короткая оценка интоксикации, QEESI, Candida, DASS-42).

Шкалы 0–3 с формулировками, различающимися по блокам. Ключ переводит сумму по блоку
в степень отклонения (низкая / средняя / высокая); у QEESI и Candida пороги различаются
по полу; DASS даёт три подшкалы (депрессия, тревожность, стресс) с пятью градациями.

Точные границы блоков дополнительных опросников уточняются при разборе файла на этапе
реализации и фиксируются эталонными тестами.

### Слой 4 — справочник специалистов (YAML)

Специальность, описание когда и с чем к ней направлять, и список доверенных врачей коуча
с контактами, форматом приёма и пометками. Собирается однократным ручным переносом из
существующего телеграм-чата через выгрузку Telegram Desktop в JSON.

Врачи видны только коучу и в клиентский PDF не попадают.

### Версионирование

Вся база знаний под контролем версий. Каждый отчёт запоминает версию, на которой собран.

## 7. Наполнение опросника

Опросник состоит из обязательного ядра (организационная часть и клинические системы) и
дополнительных модулей (системное воспаление, интоксикация, QEESI, Candida, DASS),
которые коуч включает вручную под конкретного клиента при генерации файла.

Обоснование: 565 вопросов — это 40–60 минут работы. Риск не в отказе клиента, а в том,
что хвост он дозаполнит наугад, и шум попадёт в интерпретацию как сигнал.

### Форма опросника

Автономный HTML-файл, отправляемый клиенту в мессенджере. Клиент открывает его в браузере
(включая мобильный), заполняет по блокам, прогресс сохраняется локально в браузере —
можно закрыть и вернуться позже. По завершении нажимает «Скачать ответы» и присылает
коучу полученный файл.

Ни сервера, ни регистрации, ни хранения медицинских данных у третьих лиц.

## 8. Обезличивание и приватность

Локальность защищает хранение, но интерпретация требует отправки данных модели. Поэтому
перед каждым вызовом модели данные обезличиваются.

**Уходит модели:** пол, возраст, при необходимости фаза цикла; структурированные находки;
запрос клиента и его цели; контекстный слой базы знаний; справочник специальностей.

**Не уходит:** ФИО, контакты, дата рождения, номера полисов и страховок, идентификаторы
пациента в бланках лаборатории, названия и адреса лабораторий, привязанные к пациенту.

Обратная подстановка идентифицирующих данных выполняется локально, на этапе сборки PDF.

Тест на обезличивание — обязательный и не подлежит смягчению (см. раздел 13).

## 9. Интерпретация

Модель получает находки как входные данные и свободна в их трактовке: она формирует
гипотезы, расставляет приоритеты и выбирает специальности для направления. Числовая
основа под этой трактовкой посчитана кодом и не выдумывается.

Каждый раздел черновика помечен находками, на которых он стоит, — коуч видит цепочку и
может возразить в любом звене.

Внешние ссылки на литературу в MVP не используются: источники берутся только из базы
знаний коуча, и в клиентский PDF ссылки не попадают. Обоснование остаётся в рабочем
черновике коуча.

## 10. Отчёт

Шаблон — HTML и CSS, печать через WeasyPrint. Вёрстка правится независимо от логики.

Объём 5–10 страниц. Структура:

1. Титул: имя клиента, дата, имя специалиста
2. Запрос клиента и его цели — его словами
3. Карта систем: результат опросника, степени отклонения по блокам
4. Ключевые показатели: значение, лабораторный интервал, целевой коридор коуча
5. Динамика показателей — появляется начиная со второго среза
6. На что обратить внимание с врачами: специальности и с чем к ним идти
7. Коррекция образа жизни: питание, сон, движение, стресс
8. Вспомогательные практики
9. Следующие шаги и горизонт работы
10. Дисклеймер

Контакты рекомендованных врачей в PDF не попадают — они подсвечиваются коучу в портфолио
клиента и передаются отдельно, в частном порядке.

## 11. Точки расширения

Три сменные точки с узкими контрактами. Остальные модули не знают, что за ними стоит.

| Контракт | Реализация в MVP | Возможные замены |
|---|---|---|
| `LLMProvider` — текст по запросу | Claude Code в headless-режиме (`claude -p`) на подписке Claude Max, без оплаты по токенам | API-ключ Anthropic, локальная модель, другой провайдер |
| `OCREngine` — текст из изображения | Распознавание через Claude (снимает зависимость от отдельного OCR) | Tesseract, Yandex OCR, PaddleOCR, несколько движков с голосованием |
| `PriceSource` — цена и ссылка на товар | Не используется в MVP (см. бэклог) | Каталог коуча, коннектор ВкусВилл, маркетплейсы |

Выбор реализации — настройка, а не переписывание кода.

Ограничение выбранного варианта LLM: расход считается против лимитов подписки Claude Max,
а не по токенам. На ожидаемом потоке клиентов лимиты не достигаются.

## 12. Обработка ошибок

Базовое правило: система ничего не додумывает молча. Всё неизвестное поднимается коучу.

| Ситуация | Поведение |
|---|---|
| В PDF нет текстового слоя | Автоматический переход на распознавание изображения |
| Показатель не распознан | Попадает в раздел «требует внимания» на экране сверки, не отбрасывается |
| Единицы не совпадают с референсом | Конвертация по таблице; при неизвестном пересчёте значение помечается и не трактуется |
| Показателя нет в референсах | Показывается как есть, без вердикта, с пометкой «правило не задано» |
| Одно значение встречается в двух документах | Обе версии выводятся на сверку, выбор за коучем |
| Модель недоступна или достигнут лимит | Состояние сохраняется, повтор по кнопке, черновик не теряется |

## 13. Тестирование

- **Скоринг опросника.** Эталонные наборы ответов и ожидаемые суммы со степенями, взятые
  из листа `РЕЗУЛЬТАТ КЛЮЧ`. Проверяется до последнего балла.
- **Референсы.** Таблица случаев: значение, пол и возраст на входе — ожидаемая находка на
  выходе. Включая границы интервалов и производные соотношения.
- **Парсинг PDF.** Набор реальных выгрузок разных лабораторий с зафиксированным ожидаемым
  результатом. Каждый новый формат лаборатории добавляется в набор.
- **Конвертация единиц.**
- **Обезличивание.** Через модуль прогоняются пакеты с ФИО, телефонами, датами рождения и
  номерами полисов; тест падает, если хоть что-то просочилось. Обязателен, не смягчается.
- **Сборка PDF.** Документ собирается, кириллица отображается, объём в заданных границах.

Точность интерпретации автотестами не проверяется — это оценочное суждение, выносимое
коучем на воротах черновика. Тесты гарантируют, что до коуча доходят правильные цифры и
что персональные данные не покидают машину.

## 14. Технологический стек

| Задача | Инструмент | Обоснование |
|---|---|---|
| Бэкенд и веб-интерфейс | Python, FastAPI, серверные HTML-шаблоны | Минимум клиентского кода |
| Хранение | SQLite | Один файл, переносится целиком |
| Чтение PDF | pdfplumber | Извлекает таблицы анализов со структурой |
| Распознавание изображений | Claude через `LLMProvider` | Снимает отдельную зависимость |
| Генерация PDF | WeasyPrint | HTML и CSS вместо координат, надёжная кириллица |
| Графики динамики | matplotlib | Встраиваются в HTML-шаблон |
| Разбор xlsx-опросника | openpyxl | Однократный импорт спецификации |
| Языковая модель | Claude Code headless (`claude -p`) | Работает на подписке Max, без оплаты по токенам |

## 15. Бэклог

Согласовано отложить до следующих этапов:

- **Клиентский экран с геймификацией** — личный кабинет клиента, отслеживание прогресса
  по запросу, элементы вовлечения. В MVP клиентская часть ограничена PDF-отчётом.
- **Рекомендации БАДов** — каталог коуча (нутриент, форма, дозировка, производитель,
  ссылка, цена, дата актуализации), связывание находок с категориями нутриентов, раздел
  «что купить» в клиентском PDF. Автоподтягивание цен из ВкусВилла через подключённый
  коннектор как первый источник; маркетплейсы (iHerb, Ozon, Wildberries, Яндекс.Маркет)
  требуют парсинга витрин — хрупко и в серой зоне пользовательских соглашений.
  При реализации: раздел визуально отделяется в PDF и сопровождается формулировкой коуча
  о согласовании добавок с врачом при приёме препаратов и хронических состояниях.
- **Адаптивная маршрутизация опросника** — короткий скрининг с автоматическим
  разворачиванием релевантных блоков вместо ручного выбора модулей коучем.
- **Внешние ссылки на литературу** — поиск подтверждающих публикаций с обязательной
  проверкой коучем.
